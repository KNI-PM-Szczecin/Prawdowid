# rag

Python (FastAPI). Korpus źródeł, indeksowanie i wyszukiwanie z metadanymi. Osobny serwis, `agent/` woła go przez HTTP (kontrakt: `../CONTRACT.md`). Zasady: `../AGENTS.md`. Najpierw przeczytaj `../spec`.

## Uruchomienie

Wymaga tylko Dockera. Zależności są w `pyproject.toml` i `uv.lock`, a obraz instaluje je przez `uv sync --frozen`.

W `../.env` ustaw `DATABASE_URL` (Supabase) albo, dla lokalnej bazy, `RAG_POSTGRES_PASSWORD` (bez niego profil `local-db` nie wystartuje). Ustaw też `RAG_ADMIN_TOKEN` (bez niego endpointy administracyjne są wyłączone). Hasło i token wygenerujesz poleceniem `python -c "import secrets; print(secrets.token_urlsafe(32))"`.

```
cd rag
docker compose --env-file ../.env up -d --build                      # baza w Supabase (DATABASE_URL w ../.env)
docker compose --env-file ../.env --profile local-db up -d --build   # lokalny Postgres, DATABASE_URL puste
```

Baza: `DATABASE_URL` z `../.env`, wspólna z `backend/` (Supabase, Session pooler, opis w `../README.md`). `RAG_POSTGRES_DSN` nadpisuje ją tylko dla `rag/`. Baza musi mieć rozszerzenie `pgvector` (Supabase ma je wbudowane, `rag` włącza je przy starcie; lokalnie obraz `pgvector/pgvector`). Lokalny `rag` nie powinien wskazywać bazy produkcji, bo jego seed, importy i harmonogram zmieniają korpus (szczegóły w `../docs/docker.md`, tryb z Supabase). Limit połączeń: `RAG_POSTGRES_POOL_MAX_SIZE` (5).

Lokalnie bez Dockera (Postgres z pgvector nadal z compose, profil `local-db`): `uv sync`, potem `uv run uvicorn app.main:app --port 8001`. Ustawienia czyta z `../.env` i `rag/.env` (`DATABASE_URL`, `RAG_MODEL_CACHE_DIR`). Nową paczkę dodajesz przez `uv add <paczka>`.

Serwis: `http://127.0.0.1:8001` (OpenAPI: `/docs`). Słucha tylko na localhost. Lokalny Postgres (profil `local-db`) tylko na `127.0.0.1:5432` dla `backend/` w trybie offline. Pierwszy start pobiera modele (ok. 3 GB) do wolumenu `model_cache`, kolejne starty trwają kilka sekund.

Test dymny na fikcyjnych danych:
```
curl -X POST localhost:8001/ingest -H "X-Admin-Token: $RAG_ADMIN_TOKEN" -H "Content-Type: application/json" --data-binary @tests/smoke_documents.json
```
Polskie znaki w `curl -d '...'` w Git Bash na Windows psują kodowanie, więc ciało zapytania wysyłaj z pliku UTF-8 (`--data-binary @plik.json`).

## Testy i lint

```
uv sync
uv run ruff check . && uv run ruff format --check .
uv run pytest
```
Testy nie wymagają Dockera ani modeli: czyste funkcje (chunking, stemmer, ekspansja, eviction, reguły korpusu, parser HTML, import aktów, strażnik URL, wykrywanie prompt injection) oraz endpointy na atrapach (`/search`, `/ingest`, `/fetch`, pętla zgłoszeń, uzgodnienie wektorów, uzupełnianie z gov.pl, seed, rozgrzewka). Zestaw prób prompt injection w `tests/test_injection.py` napisaliśmy sami, więc to test regresji, a nie niezależna miara skuteczności.

## Budżet czasu

Kontrakt daje rag 12 s na wywołanie. Reranker (cross-encoder na CPU) jest najdroższy i rośnie liniowo z długością tekstu, dlatego fragmenty mają 450 znaków, pula kandydatów 12, fact-checków jest maks. 10, a z katalogu kampanii rerankowanych jest 5 spraw po pierwszych 400 znakach. Metadane z Postgresa są pobierane równolegle z rerankingiem. Pomiar sprzed importu aktów prawnych i uzupełniania z gov.pl, na korpusie 104 stron (1504 fragmenty) i katalogu 201 spraw: mediana 3,3 s, przed strojeniem 6,0 s. To samo zapytanie (z filtrami i `topK`) w ciągu 10 min i przy tej samej wersji korpusu wraca z pamięci podręcznej w RAM, więc powtórzenia i drugi kanał dostają identyczną odpowiedź bez kosztu rerankera. Ekspansja przez LLM ma limit 3 s, baza po 5 s. `GET /health` sprawdza bazę, tabelę wektorów i katalog incydentów i zwraca `503 degraded`, gdy któreś nie odpowiada; kontenery mają `restart: unless-stopped`.

Rozgrzewka: przy starcie, przed przyjęciem pierwszego żądania (`app/warmup.py`), rag wykonuje pełną ścieżkę wyszukiwania na tekście spoza korpusu — trzy zapytania do modeli, trzy wyszukiwania hybrydowe w Qdrancie i rerank całej puli kandydatów. Zimny start po deployu kosztował 12,6 s i przekraczał limit `agent/`, więc pierwsze zapytanie kończyło się `technical_error`; po rozgrzewce ten koszt jest płacony przed otwarciem portu, a nie w żądaniu obywatela. Błąd rozgrzewki jest logowany i nie blokuje startu.

## Bezpieczeństwo

- `POST /ingest`, `DELETE /sources/{documentId}`, `POST /incidents`, `DELETE /incidents/{source}/{incidentId}` oraz wszystkie `POST /admin/*` (`incidents/sync`, `corpus/sync`, `corpus/fetch`, `corpus/law`, `corpus/prune`, `corpus/reconcile`, `eviction`) wymagają nagłówka `X-Admin-Token` równego `RAG_ADMIN_TOKEN`. Bez tokena zwracają 401, a gdy token nie jest skonfigurowany, 403.
- Otwarte są endpointy odczytu (`POST /search`, `GET /sources`, `/sources/catalog`, `/sources/external`, `/incidents`, `/corpus/*`, `/health`) oraz `POST /fetch` (dla `agent/`) i `POST /reports/match` (dla backendu; zapisuje zgłoszenie w kolekcji `unresolved_reports`). Ochroną jest to, że serwis słucha tylko na localhost albo w sieci wewnętrznej.
- Każdy nieobsłużony błąd zwraca `503 index_unavailable`, nigdy pustą listę udającą brak dowodów.
- Guard URL (`app/url_guard.py`): URL podany przez obywatela (i każdy cel przekierowania, bo redirecty są robione ręcznie) musi wskazywać wyłącznie publiczne adresy — http/https, porty 80/443, wszystkie wyniki DNS poza loopback, sieciami prywatnymi i link-local (w tym metadanymi chmury `169.254.169.254`). Pobieranie strumieniowe z limitem 2 MB w trakcie pobierania. Atrapy i usługi lokalne (np. `host.docker.internal` dla ekspansji LLM) tym guardem nie przechodzą i nie muszą — dotyczy on tylko URL-i od użytkownika i listy zasilania korpusu.

## Architektura

| Element | Rola |
|---|---|
| `vec_evidence_chunks`, `vec_disinfo_incidents`, `vec_unresolved_reports` (pgvector) | Po jednej tabeli na kolekcję: wektor dense (BGE-M3, 1024, indeks HNSW, kosinus), `tsvector` ze stemowanymi tokenami (indeks GIN; Supabase nie ma polskiej konfiguracji wyszukiwania, więc stemer z `app/languages/pl.json` działa w aplikacji, a baza indeksuje wynik jako `simple`) i `payload` JSONB (`chunk_id`, `source_id`, `text`, `topic_tag`, `source_type`, `published_at`; dwa ostatnie także jako kolumny do filtrów). Wyszukiwanie hybrydowe to jedno zapytanie SQL: top-N po kosinusie i top-N po `ts_rank_cd`, fuzja RRF. |
| PostgreSQL (Supabase albo lokalny) | `sources` (tytuł, wydawca, link, daty `TIMESTAMPTZ`, licencja, typ) i `document_metadata` (tier, wiarygodność, ochrona, `read_count`, soft delete). Stan zmienny (cykl życia fragmentu) jest tu, a wektory w tabelach `vec_*` tej samej bazy. Tabele mają włączone RLS bez polityk, więc REST API Supabase ich nie wystawia. |
| FastEmbed (ONNX, CPU) | BGE-M3 dense, `bge-reranker-v2-m3` (int8). Wszystko w kontenerze, bez GPU. |
| APScheduler | Import EUvsDisinfo codziennie o 2:00 (tylko z `EUVSDISINFO_TOKEN`), eviction o 3:00, uzgodnienie wektorów z metadanymi o 4:00, `VACUUM ANALYZE` tabel wektorowych o 4:30. |

Przepływ `POST /search`: ekspansja zapytania (oryginał, negacja, neutralne) → 3 równoległe zapytania hybrydowe (RRF, po 30, z filtrami `sourceTypes` i `publishedAfter` w obu połówkach zapytania SQL) → pula 12 unikalnych (najwyżej 3 fragmenty z jednego dokumentu) → reranking cross-encoderem względem oryginału → `score = sigmoid(logit / 4)` w skali 0..1, odcięcie poniżej 0,5, przy równych ocenach wygrywa nowszy fragment → gdy wyników jest mniej niż `RAG_GOV_SEARCH_MIN_RESULTS`, uzupełnianie z gov.pl i ponowne wyszukiwanie (opis niżej) → `topK` wyników (domyślnie 5, maksymalnie 7, więcej daje 422) → złączenie z metadanymi z Postgresa → **odrzucenie fragmentów bez tytułu, wydawcy, linku, daty pobrania lub daty publikacji** → blok `<dostepne_zrodla>` → w tle `read_count + 1`. Fact-check bez daty weryfikacji też nie wraca w `results`.

Pola API są w camelCase zgodnie z `../CONTRACT.md` (sekcja 3). Daty są znacznikami czasu ISO 8601; wartość bez strefy jest traktowana jako UTC. Pełny kształt odpowiedzi (`contextXml`, `expandedQueries`, `elapsedMs`, `externalSources`, `campaignAlert`, a w `Passage` `chunkId`, `tier`, `reliability`) opisuje `../CONTRACT.md` §3.

Katalog kampanii dezinformacyjnych: osobna tabela wektorowa (`vec_disinfo_incidents`) zasilana przez `POST /incidents` z tokenem admina (format: `IncidentIn` w `app/models.py`, przykład w `tests/smoke_incidents.json`). Przy każdym starcie `rag/` upsertuje `app/data/seed_incidents.json` (`RAG_SEED_INCIDENTS_ENABLED=true`, domyślnie): trzy publiczne sprawy EUvsDisinfo z linkiem, datą i licencją. Upsert, nie „tylko pusty katalog": import EUvsDisinfo (najnowsze N spraw) może wcisnąć się przed pierwsze zasilenie i wtedy sprawy demo wypadłyby z okna najnowszych — idempotentny upsert (ta sama sprawa = ten sam punkt) kosztuje przy starcie trzy embeddingi i gwarantuje ich obecność. To nadal wyłącznie kontekst (`campaignAlert`), nigdy dowód; import z EUvsDisinfo i `POST /incidents` działają bez zmian. Każde `/search` szuka też w katalogu (wektory zapytania oryginalnego) i ocenia kandydatów rerankerem względem samej tezy kampanii (`summary`), z progiem 0,7. Przy dopasowaniu odpowiedź ma `campaignAlert` z kategorią `possible_disinformation_campaign`, komunikatem i maks. 3 sprawami. Sprawy nigdy nie trafiają do `results` ani `contextXml`. Ponowny import tej samej sprawy (`source` + `incidentId`) ją aktualizuje, `DELETE /incidents/{source}/{incidentId}` usuwa. Sprawy są oceniane rerankerem po pierwszych 400 znakach tezy, bo pełne akapity EUvsDisinfo kosztowały ok. 2 s na zapytanie.

Import z EUvsDisinfo: przy ustawionym `EUVSDISINFO_TOKEN` (token w nagłówku `Authorization: Bearer`, nigdy w URL) `POST /admin/incidents/sync?maxCases=1000` z tokenem admina uruchamia w tle pobieranie najnowszych spraw z serwera MCP (`https://mcp.euvsd.info/mcp`, tryb bezstanowy, narzędzie `cases`, strony po 100). Postęp i błędy widać w `GET /incidents` (`euvsdisinfo.running`, `lastIndexed`, `lastError`, `available`). Raz na dobę o 2:00 dociąga 200 najnowszych spraw. Import jest idempotentny (ta sama sprawa = ten sam punkt), a przerwany zostawia to, co już zaindeksował. Na CPU 100 spraw to ok. 2 min, cały rejestr (19 800+) kilka godzin. Testy używają atrap HTTP, serwera nie wołają.

Google Fact Check Tools API: przy ustawionym `FACTCHECK_API_KEY` każde `/search` pyta też na żywo `claims:search` (język `pl`, limit czasu 4 s, cache 1 h z hashem zapytania jako kluczem). Oceny weryfikatorów przechodzą przez ten sam reranker i próg co korpus i wracają jako `Passage` z `sourceType: "factcheck"`. Klucz idzie w nagłówku `X-Goog-Api-Key`, nie w URL. Brak klucza, limit albo awaria Google nie psują wyszukiwania: odpowiedź ma wtedy `externalSources[].status` równe `disabled` lub `error`, a log zawiera tylko kod HTTP, bez treści zgłoszenia. Filtr `sourceTypes` bez `factcheck` w ogóle pomija to API.

Ekspansja zapytań: domyślnie regułowa. Gdy ustawione jest `RAG_EXPANSION_LLM_URL` (np. FastFlowLM: `http://host.docker.internal:52625/v1`), używa modelu. Dla hosta `api.openai.com` zapytanie wysyła `max_completion_tokens`, `reasoning_effort` z `RAG_EXPANSION_LLM_REASONING_EFFORT` (domyślnie `none`) oraz `temperature: 0` **tylko przy `none`**; dokumentacja OpenAI zabrania temperatury przy innym wysiłku rozumowania, więc wtedy `rag/` używa reguł, zamiast dopuszczać zmienne zapytania. Inne serwery dostają `temperature: 0`. Wynik ekspansji jest cache'owany po hashu twierdzenia (`RAG_EXPANSION_CACHE_TTL_SECONDS`, domyślnie 3600 s), więc powtórzone sprawdzenie ma te same zapytania pomocnicze. Przy błędzie wraca do reguł i loguje WARNING.

Prompt injection: przed dopasowaniem tekst jest normalizowany (NFKC, usunięcie znaków niewidocznych, małe litery, bez diakrytyków). Wzorce PL i EN są w `app/context.py`. Wykryty fragment ma flagę `suspected_injection` i trafia do logu, ale nadal jest zwracany jako dane.

## Język

Korpus domyślnie po polsku (`RAG_CORPUS_LANGUAGE=pl`). BM25 z FastEmbed nie ma polskiego stemmera, dlatego profil języka (stopwords i lekki stemmer sufiksowy) jest w `app/languages/pl.json`. Nowy język to nowy plik `<kod>.json`. BGE-M3 jest wielojęzyczny i dopasowuje polskie zapytania do źródeł obcojęzycznych.

## Zasilanie korpusu

Startowy korpus demo: `app/data/seed_documents.json` zawiera dosłowne fragmenty publicznych źródeł (28 w chwili pisania) z kompletem metadanych (tytuł, wydawca, data publikacji i pobrania, link, licencja). Przy starcie `rag/` indeksuje brakujące `documentId` (także te, które metadane znają, ale nie mają wektorów, np. po ręcznym czyszczeniu tabeli wektorów) przez zwykłą ścieżkę `ingest` (katalog, chunking, duplikaty). Dzięki temu fakty z `eval/cases.json` i scenariusza C są w korpusie nawet bez dostępu do stron; `RAG_SEED_CORPUS_ENABLED=false` wyłącza uzupełnianie, a błąd jednego dokumentu nie blokuje startu. Istniejące dokumenty są pomijane, więc restart nie powiela treści.

Katalog zaufanych źródeł jest w `app/data/sources_catalog.json` (`GET /sources/catalog`): wydawca, domeny, typ, tier, wiarygodność i uzasadnienie kwalifikacji, plus reguły dla typów, źródeł spoza katalogu i wykluczania. Dopasowanie po domenie URL (najdłuższa pasująca domena wygrywa, więc `isap.sejm.gov.pl` ma własny wpis mimo ogólnego `gov.pl`). Przy `POST /ingest` dla domeny z katalogu `sourceType`, `tier` i `reliability` można pominąć; dla domeny spoza katalogu trzeba je podać jawnie (inaczej `422`), a dokument jest w audycie oznaczony `inCatalog: false`. Obecność w katalogu nigdy nie wpływa na werdykt, tylko na metadane i neutralną informację o statusie źródła. Nowe źródło to nowy wpis w pliku, bez zmian w kodzie.

Import ze scrapera zespołu: scraper zapisuje strony do tabeli `ScrappedData` (`id`, `date` jako RRRRMMDD, `site`, `title`, `content`) we wspólnej bazie. `POST /admin/corpus/sync?maxDocuments=5000` (token admina, `202`) wgrywa je w tle przez zwykłą ścieżkę `ingest`: katalog nadaje typ i tier po domenie, kopie treści są pomijane, a linie powtarzające się w co najmniej 30% stron (menu, stopki) są usuwane przed podziałem na fragmenty. Postęp w `GET /corpus/sync`. Import jest idempotentny (`documentId` = `scrapped:<id>`, ponowne wgranie podmienia fragmenty). Na CPU 111 stron to ok. 8 min. Tabela `Law` (Dziennik Ustaw) ma osobny import, opis niżej.

Reguły wykluczania: `app/data/corpus_rules.json` (hosty, wzorce adresów i tytułów) odrzuca przy każdym imporcie strony-listy (aktualności, komunikaty, ostrzeżenia jako listy), strony główne portali i ministerstw oraz lokalne kroniki Policji i SOK: to same nagłówki bez daty albo treści, o które obywatel nie pyta. Takie strony liczą się w statusie jako `skippedExcluded`. `POST /admin/corpus/prune` (token admina) usuwa z indeksu dokumenty z importów zbiorczych (`scrapped:`, `web:`, `law:`) pasujące do reguł i zwraca listę `documentId`; `?dryRun=true` tylko pokazuje, co by usunął. Dokumentów wgranych ręcznie przez `POST /ingest` nie rusza. Zmiana reguły to zmiana pliku, bez kodu; pojedynczą stronę z wykluczonego serwisu nadal można wgrać przez `POST /ingest`.

Akty prawne: scraper zespołu zapisuje Dziennik Ustaw 2025–2026 do tabeli `Law` (`docid` = pozycja w roku, `date` RRRRMMDD, `doctitle`, `rule` = jeden artykuł). `POST /admin/corpus/law?maxChars=4000000` (token admina, `202`, postęp w `GET /corpus/law`) importuje akty z `app/data/law_acts.json` w kolejności z listy: dla każdego wpisu najnowszy akt pasujący do `titlePattern` (np. najnowszy tekst jednolity Kodeksu pracy), jako dokument `law:<id>` z adresem pozycji w Dzienniku Ustaw (`https://dziennikustaw.gov.pl/DU/<rok>/<pozycja>`), datą ogłoszenia jako datą publikacji i adnotacją o licencji (akt normatywny, art. 4 pkt 1 prawa autorskiego). Łamania wierszy z PDF są sklejane, akt dłuższy niż `RAG_LAW_PART_MAX_CHARS` (450 000) jest dzielony na części na granicach artykułów (`law:<id>:2`). Budżet `maxChars` ogranicza jedno uruchomienie (CPU: ok. 8 min na 500 000 znaków); kolejne uruchomienie pomija akty już wgrane z tej samej pozycji i idzie dalej. Lista to 44 akty, o które obywatele pytają najczęściej (praca, świadczenia, dokumenty, wybory, podatki, obronność, migracja, zdrowie, szkoła), nie wszystkie 1900 aktów z tabeli. Pełny zrzut (122 tys. wierszy, 137 mln znaków) nie mieści się w darmowym planie bazy, więc `PYTHONPATH=. uv run python scripts/trim_law_table.py` (dry run; `--apply` kasuje i robi `VACUUM`) zostawia w tabeli tylko akty z listy: 44 akty, 11,8 tys. wierszy, 9,4 mln znaków. Nowy akt na liście wymaga ponownego wgrania go przez scraper.

Harmonogram odświeżania (`app/maintenance.py`, APScheduler w procesie rag): lista startowa stron jest pobierana ponownie codziennie o `RAG_CORPUS_REFRESH_CRON_HOUR` (5:00; zmieniona strona podmienia swoje fragmenty i datę publikacji), akty z Dziennika Ustaw są importowane ponownie co tydzień (`RAG_LAW_REFRESH_CRON_DAY_OF_WEEK` = `mon`, `RAG_LAW_REFRESH_CRON_HOUR` = 6, budżet `RAG_LAW_REFRESH_MAX_CHARS`); nowy tekst jednolity zastępuje stary dokument `law:<id>`. `RAG_CORPUS_REFRESH_ENABLED=false` wyłącza oba zadania. Pozostałe zadania nocne: eviction (3:00), uzgodnienie wektorów z metadanymi i `VACUUM ANALYZE` (4:00/4:30), import EUvsDisinfo (2:00, gdy jest token).

Pobieranie stron z sieci: `POST /admin/corpus/fetch` (token admina, `202`) z ciałem `{"urls": [...]}` albo bez ciała, wtedy bierze listę startową `app/data/seed_urls.json` (konkretne strony z faktami z eval, dokumenty trwałe: Konstytucja, członkostwo w UE i NATO, transfery UE–Polska, oraz analizy weryfikatorów faktów o powracających mitach: 5G, szczepionki i autyzm, chemtrails, bilans składki do UE). Tekst wyciąga parser HTML ze standardowej biblioteki: bez skryptów, stylów i nagłówka dokumentu; bierze najdłuższy region `<article>`/`<main>` (co najmniej 400 znaków), a gdy go brak, stronę bez menu, paneli bocznych, stopek i formularzy; zapory antybotowe rozpoznaje po tytule i pomija. Dalej strony idą tą samą ścieżką co ze scrapera. Data publikacji pochodzi z metadanych strony (`article:published_time`, OpenGraph, JSON-LD `datePublished`, `<time datetime>`); gdy ich brak, `seed_urls.json` może przypiąć datę widoczną w treści lub w akcie prawnym. Strona bez ustalonej daty nie jest zwracana jako dowód. Strony bez tekstu w HTML (aplikacje JS, zapory anty-botowe jak Incapsula na `ulc.gov.pl` i `sar.gov.pl`), nie-HTML i błędy HTTP są pomijane i liczone jako `failed` w `GET /corpus/fetch`; zabezpieczeń serwisów nie obchodzimy. Klient przedstawia się jako `Prawdowid/0.1`, pobiera po jednej stronie z odstępem 0,5 s i limitem 2 MB. Pomiar z pierwszego przebiegu (lista miała wtedy 40 adresów, dziś 36): 27 stron wgranych. Aktualny stan korpusu (dokumenty, domeny, typy; minimum z briefu: 100, 10, 2) odczytuj z `GET /sources`, bo zmienia się po każdym imporcie i uzupełnianiu z gov.pl.

Uzupełnianie korpusu z gov.pl (`app/gov_search.py`): gdy `/search` znajdzie mniej niż `RAG_GOV_SEARCH_MIN_RESULTS` (domyślnie 1) trafnych fragmentów, rag pyta wyszukiwarkę portalu gov.pl (`/api/data/search`, ten sam endpoint co gov.pl/web/gov/szukaj; `robots.txt` pozwala na pobieranie) treścią twierdzenia. Z 10 najtrafniejszych wyników bierze najtrafniejszy (może opisywać stan dawny) i najnowsze pozostałe według daty publikacji z gov.pl, razem najwyżej `RAG_GOV_SEARCH_MAX_PAGES` (3). Strony idą przez `fetch_page` (strażnik adresów, limit rozmiaru) i zwykłą ścieżkę `ingest` (katalog, reguły wykluczania, duplikaty), z `publishedAt` z gov.pl, a potem wyszukiwanie rusza ponownie. Aktualność: najnowsze strony mają pierwszeństwo, ranking przy równych ocenach woli nowszy fragment, a kopia starsza niż `RAG_GOV_SEARCH_REFRESH_DAYS` (30) jest przy kolejnym pytaniu pobierana ponownie i zastępuje starą dopiero po udanym pobraniu. Całość mieści się w `RAG_GOV_SEARCH_BUDGET_SECONDS` (6 s) w budżecie 12 s; wolniejsze uzupełnianie kończy się w tle, więc strony trafiają do korpusu dla kolejnych pytań. Do gov.pl trafia tylko treść twierdzenia po maskowaniu danych osobowych w backendzie. Wynik w `externalSources` jako `gov_search`; wyłączenie: `RAG_GOV_SEARCH_ENABLED=false`.

Duplikaty: rag liczy skrót znormalizowanej treści (`content_hash`) i odrzuca `409` dokument o tej samej treści co inny aktywny dokument. Kopie z drobnymi zmianami łapie drugi próg: dla każdego fragmentu nowego dokumentu rag szuka najbliższego fragmentu innego dokumentu; gdy co najmniej 70% fragmentów wskazuje ten sam dokument i średnie podobieństwo kosinusowe wynosi ≥ 0,87, dokument dostaje `409` z dopiskiem „parafraza” (`RAG_NEAR_DUPLICATE_MIN_MEAN_COSINE`, `RAG_NEAR_DUPLICATE_MIN_SHARE`). Progi zmierzone na korpusie demo: ta sama strona pobrana w różnych dniach, nawet z inaczej pociętymi fragmentami, daje średnią 0,89–0,95 przy udziale 0,75–1,0; różne strony tego samego serwisu (raporty dobowe RCB, aktualności policji) albo mają średnią poniżej 0,88, albo rozpraszają dopasowania po wielu dokumentach. To zabezpieczenie celuje w kopie całych stron, nie w każdą przeróbkę: krótki tekst z edycją w połowie fragmentów przejdzie. Ponowne wgranie pod tym samym `documentId` nadal podmienia fragmenty.

Audyt źródeł zewnętrznych: `GET /sources/external` opisuje Google Fact Check, wyszukiwarkę gov.pl i EUvsDisinfo (rola, co dostaje dostawca, warunki, zmienna z kluczem) i pokazuje, czy są włączone oraz stan katalogu kampanii. Razem z `GET /sources` i `GET /sources/catalog` daje pełną listę źródeł do audytu.

Zewnętrzny zestaw prób prompt injection: `RAG_INJECTION_EVAL_FILE=<ścieżka>` (jedna próba na linię) włącza test `tests/test_injection_external.py`, który liczy odsetek wykrytych prób i wymaga ≥ 90% (próg z briefu). Bez pliku test jest pomijany. Wbudowany zestaw w `tests/test_injection.py` pisaliśmy sami, więc jest tylko regresją. Zestaw spoza zespołu, deepset/prompt-injections (`tests/data/`, opis w `tests/data/README.md`), sprawdzany jest zawsze: 80 ze 154 angielskich prób wykrytych (52%) i 0 z 398 łagodnych tekstów oznaczonych; próg regresji 50%. Zbiór liczy jako injection także prośby „nie na temat”, dlatego nie jest miarą z briefu, a odparcie prób mierzy `eval/` w scenariuszu E.

`POST /ingest` z listą `{ source: {...}, text }` (pola w `app/models.py`: `SourceIn`, przykład w `tests/smoke_documents.json`). `sourceType`: `official`, `secondary`, `factcheck`, `incident`. `reliability`: `high`, `medium`, `low`. Ponowne wysłanie tego samego `documentId` podmienia fragmenty. `DELETE /sources/{documentId}` usuwa dokument z indeksu (procedura usunięcia). Tier 1 nigdy nie jest usuwany przez eviction. Nowe fragmenty mają ochronę przez `RAG_PROTECTION_DAYS` (7).

## Eviction

Usuwa tylko wtedy, gdy liczba aktywnych fragmentów przekracza `RAG_EVICTION_MAX_ACTIVE_CHUNKS`, i tylko nadwyżkę. Kandydaci: `tier > 1` i po upływie ochrony.
`score = wiek_dni × (2.0 dla tier 3) × 0.4 − read_count × 0.6 (+30, gdy temat zajmuje > 30% bazy)`.
Nigdy nie schodzi poniżej `RAG_EVICTION_MIN_DOCUMENTS` (100) dokumentów ani `RAG_EVICTION_MIN_DOMAINS` (10) domen, czyli minimum korpusu z briefu.
Soft delete metadanych i hard delete wektorów są w jednej transakcji: gdy usunięcie wektorów zawiedzie, metadane się wycofują.

## Uzgodnienie wektorów z metadanymi

`document_metadata` jest źródłem prawdy o cyklu życia fragmentu (soft delete, eviction, prune), a wektory leżą w tabeli `vec_evidence_chunks` tej samej bazy. `ingest` zapisuje najpierw wektory, potem metadane; gdy zapis metadanych się nie uda, nowe wiersze wektorów są od razu usuwane. Mimo to po przerwanych importach zostawały wektory fragmentów, które metadane miały już jako usunięte. Taki wiersz wraca z wyszukiwania i zabiera miejsce w puli rerankera (przy zapytaniu SQL jest odrzucany dopiero przy złączeniu z metadanymi, więc wyników jest mniej niż `topK`; `search.py` odrzuca je przed wyborem puli i loguje ostrzeżenie `Skipped N of M ...`). `POST /admin/corpus/reconcile` (token admina) usuwa wiersze wektorów oznaczone w metadanych jako usunięte, oznacza jako usunięte aktywne metadane bez wektora (sieroty, np. po bazie dzielonej z innym środowiskiem; bez tego import uznałby dokument za już obecny i nigdy nie dodał wektorów) i zwraca liczbę wierszy nieznanych metadanym; `?includeUnknown=true` usuwa także te; używaj go tylko wtedy, gdy nie trwa żaden import (kod tego nie sprawdza), bo trwający import ma już wektory, a metadane dopiero po chwili. To samo uruchamia harmonogram codziennie o 4:00, przed `VACUUM ANALYZE`.

Konfiguracja: zmienne `RAG_*` (pełna lista w `app/config.py`).
